# Scale to 50,000+ customers Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (owner chose native execution). Steps use checkbox syntax.

**Goal:** Every request-time page works from database-side filtering, paging and summaries so 50,000 customers / ~1,000,000 repayments stay fast.

**Architecture:** New `lib/db.ts` (paged queries, id-chunked lookups, scope from session). Routes keep their response shape and gain optional `page`, `pageSize`, `q`, `status` params; the pages that list many rows send them. Totals move to SQL functions. Indexes and a load test come last.

**Tech Stack:** Next.js route handlers, supabase-js (PostgREST), Postgres functions/indexes (owner-approved DDL), `node --experimental-strip-types` unit tests.

**Spec:** `docs/superpowers/specs/2026-10-26-scale-design.md`

## Global Constraints
- Response shapes and permission checks stay as they are; scope (Admin all / Staff their branches' guarantors / Guarantor own / Agent assigned) moves into the query.
- `readTable` is not used for customers, loans, repayments, leads in request paths after conversion.
- DDL (indexes, functions, temporary `scale_test` schema) only after the owner approves each, shown first; no change to live rows.
- Docs and daily log updated; commits end with `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>` and `Claude-Session: https://claude.ai/code/session_016bcxF4Pr8vSXox69q1kjYf`. No `npm run build` while the dev server runs.

## Review Focus
- Search text with `, ( ) % * \` must not break the filter or inject filters.
- A Staff user with no branch sees an empty list, not everything.
- Exactly a multiple of the page size: total and last page are right.
- Guarantors with hundreds of customers: the unpaged call still returns all of theirs.
- Page 2 never repeats or skips rows (stable order with a tie-break on the id).

## Tasks
1. **`lib/db.ts`** (+ `tests/unit/db.test.ts`): `chunk`, `cleanSearch`, `pageBounds`, `pageQuery`, `byIds`, `scopeOf`.
2. **Customers list** (`GET /api/customers`): paged + search in the database; `CustomersPage` loads one page and searches on the server; other callers keep working (scoped, unpaged).
3. **Collection**: `repayments` GET, `collection-sheet`, `settlements/due`, `collections`.
4. **Leads, loans, disbursements, leads/[leadId], otp, renewalRules, paymentLinks, fileAccess**: query by id or page, never whole tables.
5. **Dashboard, reports, financial-analytics, capital, projection, commissions/payout** via SQL functions + 60 s cache; `ReportsPage` stops downloading all customers.
6. **Scores** per page of customers.
7. **Indexes** (owner approves each DDL).
8. **Load test** in schema `scale_test` (owner approves create/drop): 50,000 customers, ~1,000,000 repayments; record timings; fix what is slow.
9. **Docs**: Database Brain, Queries We Use, daily log.
